# --retail-linux32 engine-side modules vs retail Linux (depot 224, build 19307283)

Source: branch `bytematch-linux-engine` (from `bytematch` 57a94fea). Build:
`--retail-linux32 --retail-linux32-engine` in the pinned scout SDK container (gcc-9 9.3.0-17+steamrt1.3),
tree at `/data/src`; 28 modules with source (shaderapivk, chromehtml, vaudio_miles, video_bink/webm
and sourcevr are out of scope or a separate toolchain). Generated by
`devtools/bytematch/toolchain/linux/report-linux.py --engine --mac DIR` (DIR: bytematch reports of
the `--retail-osx32` modules of the round-4 integration build).

Depot 224 is a May 2025 engine build; macOS (223) and Windows (222) are November 2024. Retail Linux
is stripped: bytematch names its `.eh_frame` functions by masked search and object order
(`bytematch/elfmatch.py`). Each module's object set is what ld linked (its `-Wl,-Map`).

**Total: 66,268 / 69,246 functions (95.7%), 14,414,663 / 16,011,062 bytes (90.0%).**
engine.so: 17,614 / 17,981 functions (98.0%), 92.3% of bytes.

ToGL accounts for a large share: libtogl.so and shaderapidx9.so hold 285 / 226 / 330 of the three
classes (120 KB / 83 KB / 118 KB). Retail Linux uses the Source SDK 2013 generation of ToGL
(`IDirect3DDevice9::SetSamplerStatesNonInline` takes 7 arguments in retail libtogl.so), while this
tree has the 2018 `togl/linuxwin` (9 arguments); SDK 2013 ships only that generation's headers.

"No macOS counterpart" is mostly static-library code ld links whole on Linux and ld64 dead-strips:
tier1's `strtools.cpp`/`utlstring.cpp`/`utlbuffer.cpp` functions that no retail Linux module has
(`V_BBCodeToHTML`, `V_BasicHtmlEntityEncode`, `V_StrTrim`, `V_strtoi64`, `CUtlString::Slice/Replace/Trim*`,
`CUtlBuffer` copy constructor, ...; about 2.9 KB in every module), pathmatch in modules whose retail
copy resolved the `--wrap` symbols from libsteam_api, and `.part`/`.cold` splits.

"Line constants only": Telemetry zones carry `__LINE__` on Linux; 168 functions differ from retail
only there, because the May 2025 source has moved lines (`linuxlines.py` lists them per file). The tree
keeps one numbering for every platform, so these stay as evidence of the later revision.

## What the mode does (engine side)

- Files: the macOS manifest's object lists plus every file hl2_src's Linux VPC compiles that the
  macOS module lacks (GNU ld links whole objects; per-file `$File` conditions honoured), minus files
  retail lacks (GameUI's crypto.cpp, the texture compositor, `mathlib/vector.cpp`).
- `$GL` only for libtogl, shaderapidx9 and launcher (they link libtogl.so); the engine is a DXVK
  module (its decal code matches only without `DX_TO_GL_ABSTRACTION`), with the GL defines for
  `sys_getmodes.cpp`/`sys_mainwind.cpp` alone, which this tree compiles on Linux only so.
- makefile `PATHWRAP` (`-Wl,--wrap=fopen ...`), `-D_FILE_OFFSET_BITS=64` (retail libtier0/libvstdlib
  import `readdir64` and no `readdir`), bzip2 compiled as C++, SDK 2013 libcurl 7.21.2 + OpenSSL 1.0.1a,
  the scout image's SDL2/fontconfig/freetype, `HAVE_JPEG`/`HAVE_PNG` with the tree's jpeglib 8b and
  libpng 1.5.2 headers (the libraries themselves are old crosstool-NG prebuilts, not linked).
