Source: `bytematch-win32-8` (`bytematch` f1d88af8 merged). DLL and game rows are scoped by each module's own objects (`--own-objects`, the scope of earlier rounds); static libraries are matched against retail engine.dll when the engine links them, else against the first module that does. Cross-check: the same modules built with `--retail-osx32` against depot 223 (380 for episodic). Generated by `devtools/bytematch/toolchain/win32/report-modules.py --build build-win32 --mac-build build-retail --mac-game-build hl2=DIR --mac-game-build episodic=DIR --own-objects` (DLLs, games) and `--modules <the static libraries>` (libraries).

The matcher accepts these naming false negatives, each counted in the module's notes: call targets whose code is identical on both sides (identical-code folding), template instantiations folded in retail, and functions the symbol-port map named after a look-alike. A differing function passes when it matches exactly one unclaimed retail function; a missing retail function passes when it matches exactly one of our unpaired functions. Ties are broken by the code relocations point at and, on PE, by the string literals a function references (every MSVC dynamic initializer is named `__GLOBAL__I_a` by the port). A second pass pairs what is left: a differing retail function that is one of our unpaired functions (MSVC atexit stubs `??__F` the map named after a destructor), missing functions whose qualified name is unique on both sides but whose parameter types are spelled differently (`SOCKET`, `uint32`), with targets checked by code, and remaining ties by the map's object when every call target is verified. Two names the map swapped are paired with each other at any size when one of ours was moved onto the other's retail function, or each matches the other's; call targets are also looked up by our key (memoverride's `free` is named `_free` but referenced as `free`). C functions the map keys by Itanium signature (bzip2 is C++ on macOS) get their C names. A stripped-PE extent that runs past ours ends where the symbol-port found any function start, where an MSVC frame prologue begins on the next 16-byte boundary, or at a switch jump table pointing back into our code; a guessed start lying on a preceding stub or table plus padding moves to the boundary where ours begins.

Game rows are this build's (`client_hl2`/`server_hl2` from the episodic VPCs, as retail), in the own-objects scope; the Windows games lane reports them in the default scope, where static library objects count too.
