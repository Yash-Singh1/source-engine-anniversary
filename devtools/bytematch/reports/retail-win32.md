DLL rows are scoped by each DLL's own objects (`--own-objects`, the scope of earlier rounds); static libraries are matched against retail engine.dll when the engine links them, else against the first module that does. Cross-check: the same modules built with `--retail-osx32` against depot 223. Generated by `devtools/bytematch/toolchain/win32/report-modules.py --build build-win32 --mac-build build-retail --own-objects` (DLLs) and `--modules <the static libraries>` (libraries).

The matcher accepts these naming false negatives, each counted in the module's notes: call targets whose code is identical on both sides (identical-code folding), template instantiations folded in retail, and functions the symbol-port map named after a look-alike. A differing function passes when it matches exactly one unclaimed retail function; a missing retail function passes when it matches exactly one of our unpaired functions. Ties are broken by the code relocations point at and, on PE, by the string literals a function references (every MSVC dynamic initializer is named `__GLOBAL__I_a` by the port). A second pass pairs what is left: a differing retail function that is one of our unpaired functions (MSVC atexit stubs `??__F` the map named after a destructor), missing functions whose qualified name is unique on both sides but whose parameter types are spelled differently (`SOCKET`, `uint32`), with targets checked by code, and remaining ties by the map's object when every call target is verified. C functions the map keys by Itanium signature (bzip2 is C++ on macOS) get their C names.

Game modules (client_*, server_*, choreoobjects, particles) belong to the "Windows game modules" lane; their rows below are round 3's numbers.
